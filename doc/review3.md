# Code review — MTHREAD (MS-DOS preemptive multithreading kernel)

**Coverage:** I personally read all 2,836 lines of [mthread.asm](src/mthread/mthread.asm) plus `mthread.inc`, the headers, the FPU demos, and the Makefile; two subagents line-reviewed the input subsystem (kbd/mouse/ISRs/demos) and the video/sync-header/C++/remaining demos, cross-checking every C↔asm structure offset and constant. Findings below are ordered by severity; the headline ones I re-verified myself.

## Core kernel findings (my review)

**1. MEDIUM — Zombie-reap race can wipe a freshly created thread's TCB.** [mthread.asm:1626-1643](src/mthread/mthread.asm#L1626-L1643)
`reap_zombie_stacks` latches the stack pointer and clears `TCB_FLG_OWN_STACK` under `cli`, then executes `free()` **with interrupts enabled** (`popf` at 1626, re-`cli` only at 1639). If the timer preempts during `free()` and the scheduled thread calls `thread_create`, its own (nested) reap sees the slot as `ZOMBIE` with the flag clear, marks it `STATE_UNUSED`, and allocates it to a new thread. When the preempted thread resumes, it falls through to `reap_mark_unused` (1642-1643) and writes `flags=0, state=UNUSED` over the **new** thread's populated TCB — the created thread silently never runs, and a later `thread_create` can double-assign that TID. The same interrupt-enabled window also allows two interleaved `free()` calls on MSC 7's non-reentrant heap. Fix: keep `IF=0` from the flag-clear through the state marking (the free of a latched pointer doesn't need interrupts on), or re-validate the slot state after `free()`.

**2. MEDIUM-LOW — Idle-loop re-entry passes the wrong TID to `swap_sda_headers`, corrupting an in-DOS sleeper's SDA snapshot.** [mthread.asm:400-403](src/mthread/mthread.asm#L400-L403)
On the **first** idle entry, the scan in `schedule_next_thread` happens to leave `BL = current_tid`, so the "snapshot the outgoing thread's SDA header" call is correct. But on an **idle→idle re-entry** (`idle_hlt_spin` → `jmp schedule_next_thread` with `current_tid == NO_THREAD`), the scan starts at 0 and leaves `BL = 7` — so `swap_sda_headers` executes its save step against **TCB 7** instead of skipping (`BL == NO_THREAD`). If thread 7 is `IN_DOS` but not ready (i.e., it called `thread_sleep`/`event_wait` from inside an `INT 21h` call), the live SDA header is copied over thread 7's own snapshot; when thread 7 resumes, a stale header is restored into the SDA and its in-progress DOS call exits through the *wrong* `user_SS:SP` — stack corruption/crash. Fix: `mov bl, current_tid` (which is `NO_THREAD` on this path) before the call.

**3. LOW-MEDIUM — `isr_int24` stores `DI` into both bytes of `crit_err_code`, losing the error class in `AH`.** [mthread.asm:1141-1143](src/mthread/mthread.asm#L1141-L1143)
The variable's own comment (`mthread.asm:49`, "high=AH, low=DI") and the README say the handler records both the `AH` error class and `DI` code. But `mov ax, di` clobbers AX **before** the high byte is stored, so `thread_get_critical_error()` returns `DI` in both bytes (high byte usually 0) and the interrupted `AH` — the actual error class (write-protect, drive-not-ready, …) — is discarded. The saved AX is sitting on the stack one `pop` away; the fix is to store `AH` before loading `AX=DI`.

**4. MEDIUM-LOW (needs DOS-version validation) — IOStack calibration constant is unexplained, and failure is silent.** [mthread.asm:761-762](src/mthread/mthread.asm#L761-L762), [mthread.asm:1367-1368](src/mthread/mthread.asm#L1367-L1368)
The one-time probe computes `iostack_off = SP − (384 − 32)` measured *after* the INT 16h frame (6 bytes) and the handler's two pushes (4 bytes). For the 384-byte exchange window at [mthread.asm:505-525](src/mthread/mthread.asm#L505-L525) to coincide with the real IOStack, the DOS CON driver must push **exactly 22 bytes** below the IOStack top before issuing `INT 16h` — the "32" is an unexplained magic number, and being off shifts the swapped window so the top of the IOStack is shared between the two swapped threads (exactly the corruption the swap exists to prevent). Additionally, if the `AH=0Bh` probe never routes through `INT 16h` (a key already pending in the typeahead, or a DOS version whose CON-status path doesn't call the BIOS), `iostack_off` silently keeps the hardcoded `SDA+458h` default with no sanity check. Suggest verifying the constant per DOS version and warning if the probe didn't fire.

**5. LOW — Break handling is sticky and cumulative across Ctrl+Break.** [mthread.asm:784-785](src/mthread/mthread.asm#L784-L785), [1120-1123](src/mthread/mthread.asm#L1120-L1123), [1586-1593](src/mthread/mthread.asm#L1586-L1593)
`break_flag` is never cleared by any API (only re-zeroed in `threading_init`), so after the first break every `threading_is_break_requested()` returns 1 forever. Worse, `break_count` is incremented by *both* `isr_int1b` (Ctrl+Break) and `isr_int23` (Ctrl+C), and `isr_int1b` clears the BIOS break bit at `0040:0071h` so Ctrl+Break never reaches DOS — meaning **two Ctrl+Breaks make the user's very first Ctrl+C force-abort the program** (count hits 3), contrary to the README's "first two presses cooperative" wording.

## Input subsystem (subagent-reviewed, line-verified)

**6. MEDIUM — `kbd_getkey` check-then-act race can freeze the entire machine.** [kbd.asm:191-199](src/input/kbd.asm#L191-L199)
It probes the BDA ring (head≠tail) and then executes blocking `INT 16h AH=00h`; if the buffer emptied in between (second consumer: another thread, or CRT `_getch`), the blocking call runs under the kernel's `bios_lock`, and `isr_timer` takes the non-switching `timer_locked_tick` path — **no thread switches system-wide until any key is pressed**. Fix: `cli` from the probe through the `int 16h`.

**7. MEDIUM — `mouse_shutdown()` resets the event ring while the consumer can still be draining.** [mouse.asm:297-301](src/input/mouse.asm#L297-L301) via [cinput.c:311-327](src/demos/cinput.c#L311-L327)
Main exits as soon as `g_running==0` — which the *input thread itself* sets — then immediately resets `mouse_q_head/tail/count` with three unsynchronized stores; the input thread's final `mouse_get_event` loop can pop one stale/garbage event. Fix: join the input thread before shutdown, and/or cli-wrap the reset.

**8. LOW** — `kbd_init` early-outs on re-init *before* storing the new event pointer, so a second `MKeyboard` silently binds the old event ([kbd.asm:117-131](src/input/kbd.asm#L117-L131)); the 2-word event pointers are zeroed non-atomically at shutdown, so an interrupt in the 2-instruction window signals `DGROUP:0000`, corrupting 1 byte at the start of DGROUP data ([kbd.asm:162-163](src/input/kbd.asm#L162-L163), same in mouse); `mouse_get_state()` returns the last callback's `event_flags`, violating its documented "0 for live state query" contract ([mouse.h:35](include/mthread/mouse.h#L35)); modifier-only keystrokes never wake the input thread so the demos' "live" modifier panel goes stale ([kbd.asm:71-76](src/input/kbd.asm#L71-L76)); and the default callback mask is the magic literal `007Fh` instead of a `MOUSE_EVT_ALL` EQU ([mouse.asm:254](src/input/mouse.asm#L254)).

## Video / C++ wrappers / sync demos (subagent-reviewed; #9 verified by me)

**9. MEDIUM — `get_offset()` clamps to *physical* bounds before adding the centering offsets.** [video.c:40-41](src/video/video.c#L40-L41) (I re-verified this one directly.)
With `OFFSET_DISPLAY` active on e.g. 132×50 (`row_offset=12`, `col_offset=26`), rows 25–49 and cols 80–131 pass the physical clamp and land *outside* the centered 80×25 window — `video_putc(49,0,…)` computes cell 8052 (byte 16104), past the 13200-byte visible area, and `video_puts` spills long strings the same way. Invisible on 80×25; breaks exactly on the >80×25 modes the feature targets. Fix: clamp to the logical 25/80 window before adding offsets.

**10. MEDIUM — `MThreadManager` lifecycle is not actually thread-safe.** [mthrmgr.h:34-57](include/mthread/mthrmgr.h#L34-L57), [79-82](include/mthread/mthrmgr.h#L79-L82) (verified.)
`Initialize`/`Shutdown` correctly use `cmp_xchg` on `s_active`, but `GetInstance()`/`Release()` use plain non-atomic check-then-act (`new` on NULL `s_instance`, `++/--` on `s_ref_count`) — two threads racing `GetInstance()` leak an instance and corrupt the refcount; `Release()` racing `GetInstance()` is a use-after-free. `Abort()` also clears `s_active` *before* `threading_abort()`, so a concurrent `Initialize()` can hook the vectors and then be unhooked, leaving `s_active==1` with a dead kernel. Latent (demos call these from main only) but the class is documented as a reference-counted multi-owner manager.

**11. LOW** — `video_putu8` is only correct for 0–99: values ≥100 print a non-digit and a wrong value (`255` → "I5"), reachable via mouse columns on >100-column modes ([video.c:110-113](src/video/video.c#L110-L113), [cppinput.cpp:117](src/demos/cppinput.cpp#L117)); `video_gotoxy` does no clamping at all, asymmetric with the C side ([videohlp.asm:39-52](src/video/videohlp.asm#L39-L52)); `vram_seg` is hardcoded `0xB800` with no MDA (mode 7 → `B000h`) or graphics-mode guard ([video.c:10](src/video/video.c#L10)); none of the sync/C++ headers is self-contained (`tid_t`/`MT_ERR_*` live only in `mthread.h`, so `#include <mthread/mmutex.h>` alone doesn't compile); `MThread::GetPriority()` lacks the `MT_NO_THREAD` fallback `GetTid()` has and reports `0xFC` as a "priority" for never-created threads ([mthrd.h:90-96](include/mthread/mthrd.h#L90-L96)); and `sem_count` wraps 65535→0 silently on the 65536th no-waiter `sem_post`, contradicting the documented 0..65535 range.

## Minor notes

- **README vs Makefile default:** the README states twice that the default build is `FPU=NONE` (§"Building with NMAKE" and §Limitations 3), but the Makefile defaults to `FPU = OPTIN` — a bare `nmake` actually builds the entire FPU machinery.
- [mthread.asm:1035](src/mthread/mthread.asm#L1035): the DOS-flags mask is `0FD5h` (includes TF+IF) while the comment implies `0CD5h`; harmless in practice (DOS returns IF=1/TF=0), but constant ≠ comment.
- [mthread.asm:2585-2588](src/mthread/mthread.asm#L2585-L2588): `mutex_unlock` unconditionally restores `tcb_base_prio` on final release even if the thread still holds *other* mutexes whose waiters boosted it (the same-thread flavor of the documented single-hop PI limitation).
- [mthread.asm:98](src/mthread/mthread.asm#L98): `in_scheduler` is declared as a scheduler reentrancy guard but never used (currently safe only because the scheduler always runs with IF=0 and never re-enables until IRET).
- [mthread.inc:17-19](include/mthread/mthread.inc#L17-L19): `SHL_IMM`'s 8086 guard checks `IFIDNI <dest>, <cx>` but not `cl`/`ch`; with count>4 and `dest=cl` the macro would corrupt its own count register (all current call sites use `bx,6`, so latent).
- `threading_init` never checks the DOS version before `INT 21h AX=5D06h`; on DOS 2.x the SDA pointer is garbage and the first preempt of an in-DOS thread copies through a bogus pointer. Similarly, `thread_create`'s TCB-slot scan isn't cli-protected, so concurrent `thread_create` calls (which the README's heap-serialization advice doesn't obviously cover) can both claim the same slot.

## What checked out clean

The deep verification found the *hard* parts correct: all asm↔C structure offsets/sizes and error-code constants match exactly; the count-based mouse ring buffer (including coalescing and the full-queue overwrite path) has no off-by-one; there is no lost-wakeup window between `event_set_isr` and `event_wait` (both fully cli-protected); `cmp_xchg` is genuinely interrupt-atomic via `pushf/cli`; the INT 25h/26h "left-on-stack FLAGS" wrappers, the SDA-header ping-pong protocol, the PIT divisor math, the seeded `func(arg)`→`thread_exit` stack frame, the direct-handoff semantics of the mutex/semaphore/condvar paths, and the BIOS INT 09h chain's register/flag discipline are all correct. The demos' API usage (mutex ownership around `cond_wait`, RAII recursion depth, shutdown wake ordering, printf formats, screen geometry) also checks out.

The two findings I'd fix first are **#1** (zombie-reap race — a real corruption path in any create/join-heavy workload) and **#9** (video centering — breaks the exact feature `OFFSET_DISPLAY` exists for); #2 and #4 are worth fixing or validating on real DOS before trusting the IOStack-collision path.
